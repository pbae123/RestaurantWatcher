# 0001. Use browser automation (Playwright) instead of calling CatchTable's API directly

## Status

Accepted

## Context

RestaurantWatcher needs to read reservation availability from CatchTable's page for
a single restaurant (Jungsik). Two approaches were considered:

1. **Call CatchTable's internal API directly** (`api.catchtable.net`), parsing the
   JSON responses without a browser.
2. **Drive a real (headless) browser** against the rendered page and read
   availability out of the DOM.

Investigation of the live site (via browser network inspection) found:

- The endpoints that return day/time availability are named `dayslot-enc` and
  `timeslot-enc`. Their request bodies are a single opaque encrypted field
  (`{"data": "<ciphertext>"}`), generated by CatchTable's frontend JavaScript.
  Calling these endpoints directly would require extracting and reimplementing
  their encryption scheme from minified client-side JS.
- The site issues a Cloudflare `__cf_bm` bot-management cookie, which Cloudflare
  grants after evaluating a JS challenge in a real browser session. Plain HTTP
  requests without this cookie are likely to be blocked or rate-limited by
  Cloudflare regardless of whether the encrypted payload is solved.
- By contrast, loading the actual page in a headless browser and reading the
  rendered calendar and time-slot elements works today, satisfies Cloudflare's
  check naturally (a real browser engine runs the real JS), and requires no
  reverse-engineering of CatchTable's encryption.

## Decision

RestaurantWatcher will use Playwright to load the CatchTable shop page and read
availability from the rendered page content, rather than calling CatchTable's API
endpoints directly.

## Consequences

- The scraper depends on a browser runtime in CI (heavier CI job, slower per run
  than a raw HTTP call), and is exposed to breakage if CatchTable changes the
  *visible* calendar/time-slot UI.
- The scraper is not exposed to breakage from CatchTable rotating their request
  encryption scheme, since it never constructs or sends an encrypted payload.
- If CatchTable's Cloudflare configuration becomes hostile to headless browsers
  specifically (e.g. stricter fingerprinting), this decision would need to be
  revisited — at which point a new ADR should supersede this one rather than
  editing it in place.
